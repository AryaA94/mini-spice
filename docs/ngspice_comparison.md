# Cross-validation against ngspice

Generated by `python3 tools/compare_to_spice.py` (requires `ngspice` on
`PATH`). Every row runs the *same netlist* (see `examples/`) through both
mini-spice and ngspice 42 and reports percent error. See that script for
exactly how each value is extracted.

Two methodology notes, so the transient rows' nonzero error isn't mistaken
for a bug:

1. **ngspice's transient solver uses adaptive step control with trapezoidal
   integration by default**, not the fixed-step backward Euler this project
   uses. The `UIC` flag on every `.tran` card makes both engines start from
   the same initial conditions (see DESIGN_DECISIONS.md), but their
   per-step numerics still differ, and trapezoidal integration is
   second-order accurate versus backward Euler's first-order. Nonzero
   error on the transient rows is expected and is the same order of
   magnitude as the analytic-vs-simulated error already measured in
   `tests/unit/test_transient_analytic.cpp`.
2. **DC and AC rows show exactly 0.0000% error.** That's not rounding
   luck: DC operating point and AC sweep are both a single linear solve
   with no time discretization at all, so two correct MNA implementations
   solving the same system should agree to floating-point precision --
   and here they do.

Max error across all 39 checkpoints: **2.4759%**, on the SIN-source
checkpoint at t=6ms. That's not a larger *absolute* error than its
neighbours -- every SIN row is off by about the same ~0.011V -- it's the
same absolute error divided by a smaller value (V(out) is 0.44V there,
versus 1.5-2.8V at the other checkpoints). The next-largest, 1.58%, is an
underdamped RLC transient checkpoint sampled near a zero-crossing of the
ringing waveform (where a fixed percentage of a fast-changing signal is
most sensitive to a small timing offset between two different
adaptive/fixed step schemes).
Every DC and AC checkpoint matches to float precision or near it. The PNP
rows are the *exact* negation of the NPN rows above them, as expected from
the mirror-model construction (DESIGN_DECISIONS.md #14). The VCVS/VCCS
rows use ngspice's native `E`/`G` syntax directly (no `.model` card
needed, since these are ideal linear elements) and match to float
precision, same as every other purely-linear component.

## The PULSE/SIN rows, and checking their error is discretization, not a bug

The `PULSE RC filter` and `SIN source` rows run `examples/12_pulse_rc_filter`
and `examples/13_sine_source` at the same `dt=2e-5` their committed
`transient.csv` files were generated with. That step is fairly coarse
against these circuits' time constants (`dt/RC` is 0.02 for the PULSE
filter but 0.2 for the SIN filter, whose `RC` is 100us), so the SIN rows
carry the largest transient error in the table. To confirm that error is
backward Euler's ordinary first-order truncation error and not something
wrong with how the source is evaluated, the SIN comparison was re-run by
hand at a 10x smaller step (ngspice's reference trace computed at
`tstep=2e-6` both times):

| mini-spice `dt` | max \|V(out) error\| over the 5 SIN checkpoints |
|---|---|
| `2e-5` | 0.01613 V |
| `2e-6` | 0.00162 V |

A 10x smaller step gives a 10x smaller error: exactly first-order
convergence, which is what backward Euler should show. A wrong waveform
*parameter* (say, a swapped TD and TR) would not behave like this: it
leaves an error floor that stops shrinking once `dt` is small. What this
check *can't* rule out on its own is evaluating the source at the wrong
end of the step (`t-dt` instead of `t`), since that also shrinks as
O(dt). That's why the source's timing is checked separately, with no
integration error in the way at all, by `test_waveforms.cpp`'s
pure-resistive test (see DESIGN_DECISIONS.md #17), where `V(node)` must
track the source's exact value at each step's end time to `1e-9`.

## AC analysis of nonlinear (diode/BJT) circuits: validated a different way

The DC and AC rows above don't include a diode/BJT *AC* row, on purpose:
that path is validated in `tests/unit/test_diode.cpp` and
`tests/unit/test_bjt.cpp` against a method that doesn't touch ngspice or
this solver's own AC code at all -- perturbing the DC source by a tiny
`+-eps`, solving twice, and comparing the finite-difference slope to the
AC solver's small-signal gain. Both circuits have no reactive elements, so
the true response is frequency-independent, and the two numbers should
agree at any frequency. They do, to 9+ significant figures for both the
diode and BJT cases (see DESIGN_DECISIONS.md #16 for the numbers and the
full reasoning) -- tighter agreement than adding a third ngspice
cross-check would meaningfully improve on, which is why one wasn't added
here.

## A third method for the diode row: Lambert W

DC and AC rows above are validated two ways (this solver vs. ngspice). The
diode row gets a third, independent check that doesn't involve ngspice at
all: the diode+resistor circuit has a genuine closed-form solution via the
Lambert W function (derived in `docs/DESIGN_DECISIONS.md` #12), computed
once with `scipy.special.lambertw` and hardcoded into
`tests/unit/test_diode.cpp`. All three -- this solver, ngspice, and the
Lambert-W closed form -- agree to within the table's 0.0004%. That
agreement is also what caught a real bug during development: the first
version of this solver used a thermal voltage `Vt` computed at a flat
300K, which the Lambert-W check confirmed was *internally consistent*
(solver matched the closed form built on the same 300K assumption) but
didn't match ngspice's default 300.15K (27C, SPICE's standard `TNOM`)
convention -- a ~0.35mV discrepancy that traced to a physical-constant
choice, not a solver bug, and was fixed by matching SPICE's convention.

## A third (and fourth) method for the BJT rows

The two BJT rows are each cross-checked a third way too, against a
from-scratch Newton-Raphson solve written independently in Python (not
reusing this solver's code) -- and deliberately via *two different*
methods, one per case, in `tests/unit/test_bjt.cpp`:

- **Fixed-bias case**: a hand-derived analytic Jacobian (the same
  four-term gpi/gmr/gmf/go formulas documented in
  `docs/DESIGN_DECISIONS.md` #13, transcribed fresh into Python).
- **Emitter-degeneration case**: a numerical (finite-difference)
  Jacobian -- a genuinely black-box method that doesn't touch the
  analytic derivative formulas at all, so a transcription error in either
  the C++ implementation or the first Python check wouldn't be able to
  hide from this one.

Both Python solves converge to KCL residuals on the order of `1e-18` to
`1e-20` (effectively exact), and both agree with this solver to the full
precision reported (10 significant figures) -- not just to the ~5
significant figures ngspice agrees to. The small residual gap between
this solver and ngspice on the BJT rows is the same expected
cross-implementation-tolerance pattern seen on the diode row, not a
modeling discrepancy: both this solver's from-scratch Python check and
ngspice are independently confirming the *same* answer.
